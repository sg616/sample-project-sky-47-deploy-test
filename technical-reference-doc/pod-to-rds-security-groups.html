Pod to RDS: Why Your Security Group Rule Didn't Match

You allowed the node subnet — and the database still timed out. The missing piece is understanding whose IP the packet actually carries when a Kubernetes pod talks to a managed database. A field-guide based on a real CCE + RDS incident.

This reference explains the full chain of concepts behind the classic problem: a pod in a Kubernetes cluster can't reach a database, even though the subnet is allowed in the security group. It covers what the error signatures mean, the two fundamental cluster network models (overlay with SNAT vs. ENI/VPC-native), how security groups actually evaluate packets, and a repeatable method for diagnosing and fixing the problem. Written from a real incident — Spring Boot on CCE, HikariCP failing to connect to MySQL 5.7 with connect timed out — and the concepts generalize to AWS EKS, Azure AKS and any cloud.

How to use this If you are mid-incident, jump to the method and then to entry 01 to read your exact error signature. The model chapters (02–03) explain why the fix works; entry 05 gives the decision matrix for what CIDR to allow.

The Method

Five Steps to Any Pod→Service Connection Failure

The same procedure works whether the target is RDS, Redis, Kafka or another VPC service. Run the steps in order — most incidents are solved at step 1 or 3.

1

Read the signature, don't guess

The exception text tells you which layer failed. connect timed out → packets dropped (SG / routing). Connection refused → host reachable, port closed. Access denied → TCP works, auth failed. UnknownHostException → DNS, not network. See entry 01.

2

Establish the network model

Find out how the cluster gives pods their addresses: overlay (pod IPs live in a private container network) or ENI/VPC-native (pod IPs are real VPC addresses). This decides whose IP your traffic carries — the node's or the pod's. See entries 02 and 03.

3

Trace the packet's source IP

Ask: what source IP does the destination see? Overlay cluster leaving the cluster → node IP after SNAT. Turbo/ENI cluster → the pod IP itself. The SG rule must match that IP, not whichever one you first thought of.

4

Allow both CIDRs while you learn

Add inbound rules for the node subnet and the container CIDR. They are cheap, they are harmless, and together they cover both models — so a wrong guess about step 2 can't keep you stuck. See entry 05.

5

Prove it with a real TCP probe

Run nc -zv from a disposable pod in the cluster, not from your laptop. Green = fixed; restart the workload to recover. See entry 06.

The vocabulary shared terms

Pod CIDR / Container CIDR

The IP range Kubernetes assigns to pods, e.g. 172.16.0.0/16. Set at cluster creation (Container CIDR Block in CCE console, --cluster-cidr / EKS CNI custom networking equivalent). Visible via kubectl get pods -o wide.

Node / Subnet CIDR

The VPC subnet range the cluster worker nodes live in, e.g. 10.10.1.0/24. This is the address range external services see in overlay clusters after SNAT.

SNAT (Source NAT)

Rewriting a packet's source IP as it leaves the node — the pod's private overlay address is replaced by the node's VPC address so the outside world can route replies back.

ENI (Elastic Network Interface)

A virtual NIC attached to a VM. In Turbo/ENI clusters each pod gets one (or a shared one), making the pod IP routable inside the VPC — no SNAT needed on the way out.

01. Reading failure signatures: timeout ≠ access denied
The one idea

Every layer of the stack fails with its own unmistakable signature. connect timed out means your packet vanished on the way — a security group or routing problem — and no amount of credential or schema fixing will help until packets get through.

The signature table
connect timed out
SYN sent, no reply at all (or a silent drop). The firewall/security group dropped the packet, or there is no route. Why this matters: it is the one signature that is never about the application — fix the network first.
Connection refused
The host answered with an RST. Packets flow; the port is closed or the DB isn't listening on that port/interface. Network is fine.
Access denied for user
Full TCP handshake + MySQL protocol exchange succeeded; authentication failed. Wrong user/password, or the DB user is host-restricted.
UnknownHostException
DNS lookup failed before any packet was sent. Hostname wrong, or CoreDNS/VPC DNS not resolving it.
Communications link failure
JDBC's umbrella message — always read the Caused by: line; that's where the real signature lives.
Gotcha Don't read only the top line. In the incident the top of the stack said CommunicationsException — which sounds like "any network problem" — while the true cause, java.net.SocketTimeoutException: connect timed out, sat three Caused by levels down.
In practice~2 min
Frame
Pull the pod logs and find the deepest Caused by: — that is the layer that failed.
Go deep
Map it against the signature table: timeout → packets dropped (SG/route), refused → port, denied → auth, unknown host → DNS.
Land it
Say the verdict before touching anything: "this is a dropped-packet problem, so we fix the security group, not the credentials."
Do these three things
  1. kubectl logs deploy/backend -n sample-app — read to the last Caused by.
  2. Note the pod IP and the node IP — you'll need both in entry 03.
  3. If it's a timeout, skip everything credential-related and jump to the network model.
Red flag — don'tDon't rotate DB passwords or recreate the user when the signature is a timeout. The TCP handshake never finished — the DB never saw your credentials at all.
Part II · The Two Network Models

Whose IP Does the Database See?

The whole article turns on one question. Two architectures give two different answers — and two different security-group rules.

Model A · overlay

↑ Contents
02. Overlay / VPC-network clusters: pods hide behind the node
The one idea

In the classic model, pod IPs are private to the cluster. When a pod talks to anything outside the cluster, the node performs SNAT and the outside world sees the node's IP — so the DB security group must allow the node subnet.

How the model works

Addressing

  • Pods get IPs from the container CIDR (172.16.x.x)
  • VPC routers know nothing about that range
  • Only nodes can route to pod IPs

Leaving the cluster

  • Pod → external target hits the node's POSTROUTING chain
  • masquerade rewrites source to the node IP
  • Replies come back to the node, get de-NATed to the pod

Implication for SGs

  • RDS sees src = node IP
  • Rule must allow the node subnet CIDR
  • Pod-CIDR rule alone matches nothing here
Key concept — SNAT is what makes pod→outside-VPC possible Without SNAT, the RDS instance would receive packets from 172.16.0.126 — an address it has no route to — and could never reply. Masquerading is the bridge between the cluster-private overlay and the VPC. Same mechanism, everywhere: AWS EKS with standard CNI and AWS_VPC_K8S_CNI_EXTERNALSNAT=false, AKS kubenet, vanilla flannel/calico clusters.

Model B · ENI / Turbo

↑ Contents
03. CCE Turbo / ENI clusters: the pod is a first-class VPC citizen
The one idea

In ENI-based clusters (CCE Turbo; the EKS equivalent is giving pods their own security-group-bearing ENIs via a CNI plugin), each pod's IP is a real, routable VPC address. There is no SNAT on the way out — the database sees the pod's own IP, so the node-subnet rule alone never matches.

Trade-offs
ENI / Turbo
Pods are first-class VPC citizens: routable, per-pod security groups possible, no tunnel overhead. Cost: SGs/ACLs must be pod-CIDR-aware; ENI quota per node caps pod density.
Assuming overlay everywhere
The reflex "allow the node subnet" silently does nothing on ENI clusters — you get the same timeout and burn hours wondering why the rule "doesn't work".
Note — which one do you have? Cluster console → Basic Information → Networking shows the network model (CCE: "VPC network" vs "Cloud Native 2.0/Turbo") and the Container CIDR Block. Quick test: if kubectl get pods -o wide shows pod IPs in a range that the console lists as a VPC subnet, you're on ENI.

The rule engine

↑ Contents
04. How security groups actually evaluate a packet
The one idea

A security group is a stateful matcher on the connection's 5-tuple — and it matches on what it observes on the wire, not on what you intended. If the observed source IP isn't in any ALLOW rule, the packet is silently dropped: no error, no reply, hence connect timed out.

What the matcher sees
5-tuple match
Source IP, destination IP, protocol, source port, destination port. Your rule "TCP 3306 from 10.10.1.0/24" only fires if all five line up — in the incident, the source IP didn't.
Stateful
Once a connection is allowed out or in, return traffic is allowed automatically. You never need a matching egress rule for the DB's replies — only for the initial SYN.
Default deny
No matching allow rule = drop. Drops produce no ICMP — the client retransmits the SYN until its connect timeout expires. That silence is exactly the SocketTimeoutException signature.
Attachment point
The SG is attached to the DB instance's interface (or its ENIs). Every packet is evaluated at arrival, against whatever source IP survives SNAT — which is the whole point of entries 02/03.
Key concept — drop vs. refuse A security group drops (silence → timeout). An application or host firewall like iptables can refuse (RST → connection refused). Two different failure signatures from "the port is blocked" — entry 01 tells them apart.

Decision · what to allow

↑ Contents
05. Decision matrix: what CIDR to allow on the DB
The one idea

You rarely need to know the exact network model to get unblocked: allow both the node subnet and the pod CIDR, tighten later. Each rule covers one model; together they cover both — and each rule only permits TCP/3306, nothing else.

The options
Node subnet only
Matches overlay clusters; matches nothing on ENI clusters — the exact failure from the incident.
Pod CIDR only
Matches ENI clusters; on overlay clusters the DB never sees pod IPs (SNAT), so this also fails — just mirrored.
0.0.0.0/0
Always "works" and is a fine 5-minute diagnostic. Leaving it in place exposes the DB port to the whole internet/VPC. Never the final state for a database.
Node subnet + pod CIDR
Two narrow inbound rules for TCP/3306. Covers both network models, survives a model you misidentified, and stays least-privilege. This is the recommended end state.
Concrete rules — the incident's fix

Rule 1 — nodes

  • TCP, port 3306
  • Source 10.10.1.0/24
  • = worker node subnet

Rule 2 — pods

  • TCP, port 3306
  • Source 172.16.0.0/16
  • = container CIDR — the fix

Find the pod CIDR

  • Console: cluster Basic Info → Container CIDR Block
  • kubectl get pods -o wide — infer the range
  • kubectl cluster-info dump | grep -i cluster-cidr
Gotcha — same VPC is still required Correct CIDRs don't help across VPCs. If the DB and the cluster live in different VPCs with no peering, packets have no route and you get the same connect timed out. Check VPC membership before tuning rules.

Verify · prove it

↑ Contents
06. Verifying connectivity from inside the cluster
The one idea

Test from inside the cluster, not from your laptop — your laptop takes a completely different network path. One disposable pod doing a raw TCP connect is the ground truth for whether the SG/route problem is fixed.

The probe
nc probe pod
kubectl run nettest --rm -it --image=busybox -n sample-app --restart=Never -- nc -zv -w 3 <DB_HOST> 3306 — open means the packet path works end-to-end.
timed out result
Still dropped — re-check the CIDRs (entry 05), the VPC membership, and that you edited the security group attached to the DB, not the cluster nodes.
refused result
Network is fixed; the port isn't listening — wrong host/port, or the DB listens on a different interface. Progress, different problem.
Recover the app
kubectl rollout restart deploy/backend -n sample-app — a fresh HikariCP pool initialization now succeeds; confirm with GET /api/info → "database":{"status":"UP"}.
In practice~3 min
Frame
The probe pod must run in the same namespace/VPC path as the workload — testing from your laptop proves nothing.
Go deep
open → fix confirmed; timed out → still a drop (back to entry 05); refused → network fixed, port problem.
Land it
Restart the deployment so the connection pool re-initializes, then hit /api/info and see "status":"UP" with the MySQL version reported.
Do these three things
  1. Run the nc probe pod; --rm cleans it up automatically.
  2. kubectl rollout restart deploy/backend -n sample-app and wait for Ready.
  3. curl http://<EXTERNAL-IP>/api/info — expect "database":{"status":"UP","product":"MySQL","version":"5.7.44"}.
Red flag — don'tDon't declare victory from the probe alone. The probe pod may schedule on a node whose path differs from the app's; the real proof is the application's own health endpoint reporting UP.
